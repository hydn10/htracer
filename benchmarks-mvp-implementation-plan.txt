HTRACER BENCHMARKS MVP IMPLEMENTATION PLAN
==========================================

Status
------

This document proposes a concrete implementation of the MVP defined in
benchmarks-feature-design.txt. It is an implementation plan, not implemented
code.

The proposal intentionally keeps the first version small. Extension points are
included only where they prevent avoidable redesign later.


1. Implementation outcome
-------------------------

The MVP produces one optional executable:

  htracer-benchmarks

It supports:

  htracer-benchmarks --list
  htracer-benchmarks --suite quick
  htracer-benchmarks --benchmark render [render options]

The executable can run a fixed quick suite or one custom render configuration.
It prints a console summary and optionally writes a versioned JSON result.

The benchmark runner is an htracer application alongside ray. Enabling
HTRACER_BUILD_APPS builds and installs both executables. Normal CI compiles the
runner on Windows/MSVC and Linux/GCC and runs only its --list smoke test.


2. Implementation principles
-----------------------------

* Keep benchmark code outside the library and consume htracer through its
  public rendering API.
* Use plain data structures for configuration and results. Do not build a
  generic benchmark framework.
* Parse runtime choices into one fully validated configuration before invoking
  templated rendering code.
* Dispatch runtime precision and execution-policy choices to a small, explicit
  set of template instantiations.
* Use the same run_case() path for canonical suite cases and custom cases.
* Keep scene construction, validation, hashing, and reporting outside timed
  regions.
* Store raw integer durations so future tools can calculate different
  statistics without rerunning benchmarks.
* Version the result schema and canonical workloads independently.
* Prefer adding fields to the configuration/result model later over adding
  speculative abstractions now.


3. Proposed file layout
-----------------------

  apps/
    benchmarks/
      CMakeLists.txt
      src/
        main.cpp
        cli.cpp
        render_benchmark.cpp
        suite.cpp
        report.cpp
      include/
        htracer_benchmarks/
          model.hpp
          cli.hpp
          scenes.hpp
          render_benchmark.hpp
          suite.hpp
          report.hpp

Internal application headers are included with a qualified prefix:

  #include <htracer_benchmarks/cli.hpp>

This makes their ownership clear and avoids relative or ambiguous includes.
The include directory is supplied by a PRIVATE HEADERS file set in
target_sources(), not by a separate target_include_directories() call.

Responsibilities:

main.cpp
  Parse an invocation, select list/suite/custom mode, run cases, print results,
  optionally write JSON, and map failures to process exit codes.

model.hpp
  Own enums and plain configuration/result structures shared by the runner,
  CLI, suites, and reports. It should not depend on htracer headers.

cli.hpp / cli.cpp
  Parse arguments into a raw invocation and validate/resolve them into concrete
  benchmark cases. Produce specific diagnostic messages.

scenes.hpp
  Templated scene factories for float and double. Scene generation stays here
  because the scene type depends on the floating-point type.

render_benchmark.hpp / render_benchmark.cpp
  Dispatch a validated render configuration, run warmups and measurements,
  validate/hash images, and return a result. Template-dependent implementation
  may need to remain in the header; non-template orchestration should remain in
  the source file where practical.

suite.hpp / suite.cpp
  Return the explicit list of canonical quick-suite cases. Canonical case IDs
  and parameters live in one place.

report.hpp / report.cpp
  Compute presentation values, print the console table, gather basic build
  metadata, and write the project-specific JSON format.

This split is a target, not a requirement to preserve tiny files. During
implementation, closely coupled files may be combined if the separation adds
more navigation than clarity.


4. Core data model
------------------

Use enums rather than strings after parsing:

  enum class scene_kind { mixed, traversal, rng_probe };
  enum class rendering_kind { deterministic, randomized };
  enum class precision_kind { f32, f64 };
  enum class policy_kind { seq, par };
  enum class batcher_kind { column };
  enum class sensor_kind { point, uniform };
  enum class lens_kind { pinhole };

The single-value component enums are intentional but modest. They record the
effective configuration in results and provide a direct extension point when
pixel batching or thin lenses are added. They do not require generic component
registration or runtime polymorphism.

Suggested configuration structures:

  struct render_configuration
  {
    scene_kind scene;
    rendering_kind rendering;
    precision_kind precision;
    policy_kind policy;

    batcher_kind batcher;
    sensor_kind sensor;
    lens_kind lens;

    std::uint32_t width;
    std::uint32_t height;
    std::optional<std::uint32_t> geometry_count;
    std::optional<std::uint32_t> samples_per_pixel;
    std::optional<std::uint64_t> seed;
  };

  struct measurement_configuration
  {
    std::uint32_t warmup_count;
    std::uint32_t repetition_count;
  };

  struct benchmark_case
  {
    std::string id;
    bool canonical;
    render_configuration render;
    measurement_configuration measurement;
  };

The rendering kind disambiguates an absent seed:

* Deterministic: samples and seed are absent.
* Randomized unseeded: samples are present and seed is absent.
* Randomized seeded: samples and seed are present.

Suggested result structures:

  struct duration_summary
  {
    std::uint64_t minimum_ns;
    std::uint64_t median_ns;
    std::uint64_t maximum_ns;
  };

  struct benchmark_result
  {
    benchmark_case benchmark;
    std::vector<std::uint64_t> samples_ns;
    duration_summary summary;
    std::uint64_t checksum;
  };

Environment metadata and a vector of benchmark_result objects form one
run_report. Derived floating-point throughput values can be calculated during
reporting from integer parameters and median_ns; they do not need to be stored
as mutable runner state.

All effective component selections must be serialized, even when they are not
yet exposed as custom CLI options. This makes old results interpretable after
new options are introduced.


5. CLI parsing and validation
-----------------------------

5.1 Parsing approach

Implement a small argv parser supporting long options followed by values. Do
not add a CLI dependency and do not implement aliases, combined short flags,
configuration files, lists, ranges, or shell-like parsing.

Recognized top-level forms:

  --help
  --list
  --suite quick [--output PATH]
  --benchmark render [render and measurement options]

Top-level modes are mutually exclusive. Unknown and duplicate options are
errors. Diagnostics go to stderr and include the invalid option/value and a
short usage hint.

5.2 Custom render options

Required for a custom render:

* --scene mixed|traversal|rng-probe
* --rendering deterministic|randomized
* --width N
* --height N
* --precision float|double
* --policy seq|par

Conditionally required:

* --geometry-count N for traversal; invalid for other MVP scenes.
* --samples N for randomized rendering; invalid for deterministic rendering.

Optional:

* --seed none|INTEGER for randomized rendering. INTEGER is an unsigned decimal
  64-bit value. Omission means unseeded.
* --warmup N, default 1. Zero is valid.
* --repetitions N, default 9. Zero is invalid.
* --output PATH. Omission means console output only.

The selected rendering mode determines MVP components:

* deterministic -> point sensor, pinhole lens, column batcher
* randomized -> uniform sensor, pinhole lens, column batcher

The rng-probe scene is valid only for randomized rendering.

5.3 Numeric validation

Parse unsigned integers with std::from_chars and require complete consumption
of the input string. Reject signs, whitespace inside values, overflow, zero
width/height/samples/repetitions, and geometry_count less than 1.

Before rendering, check that width * height can be represented by std::size_t
and by the image allocation expected by htracer. Avoid an arbitrary low hard
cap that would prevent legitimate stress experiments. Allocation failure should
produce a clear runtime error rather than an uncaught exception.

5.4 Validation architecture

Keep raw parsed options separate from render_configuration. Raw fields may be
optional; a render_configuration exists only after all defaults and
cross-option rules have been resolved. Rendering and reporting code should not
need to revalidate CLI semantics.


6. Runtime-to-template dispatch
------------------------------

The library's precision and execution policies are compile-time types, while
the CLI selects them at runtime. Use explicit branching rather than type
erasure or a registration framework.

Conceptual flow:

  run_case(case)
    switch precision
      f32 -> run_typed<float>(case)
      f64 -> run_typed<double>(case)

  run_typed<Float>(case)
    build typed scene and camera
    switch rendering kind
      deterministic -> construct point/pinhole renderer
      randomized    -> construct uniform/pinhole renderer
    switch policy
      seq -> measure lambda calling renderer.render(seq, ...)
      par -> measure lambda calling renderer.render(par, ...)

For randomized rendering, branch once outside the measurement loop between
seeded and unseeded render calls. The timed callable must contain only the
public render() invocation, not repeated runtime option resolution.

This produces a small number of explicit instantiations and keeps compiler
optimization through the header-only renderer intact. Future component choices
can add another explicit dispatch branch without changing the harness or data
model.


7. Scene implementation
-----------------------

All factories are templated on Float, deterministic, and invoked before any
warmup or timed render.

7.1 mixed

Reuse the shape of the existing ray-program scene:

* Several spheres and planes.
* Two lights.
* A mix of solid and reflective materials.
* Fixed camera pose and field of view.

Do not call the ray application's private scene builder or move benchmark
fixtures into the library. The benchmark owns its stable scene definition.

7.2 traversal

Generate exactly --geometry-count objects:

* Object zero is a fixed visible sphere with an ambient/non-reflective material.
* Remaining spheres are placed deterministically outside the camera frustum so
  they are tested and rejected without changing the visible output.
* Use no reflection and minimal fixed lighting, or ambient-only material, so
  object traversal dominates and shadow-ray multiplication does not obscure
  the meaning of the experiment.

The reported geometry count is the actual total number of objects in the
scene. Tests during implementation must confirm that output is unchanged as
the count grows for deterministic rendering.

7.3 rng-probe

Use the standard uniform sensor and pinhole lens with a deliberately cheap
scene whose output depends on sample jitter. A candidate is a simple sphere
silhouette positioned so jitter near object boundaries changes hit/miss output.
Keep lights and reflection absent or minimal.

The probe must satisfy both conditions:

* Randomized coordinates affect the observable image/checksum, preventing the
  optimizer from proving RNG work irrelevant.
* Tracing remains cheap enough that seeded/unseeded provider differences are
  measurable, particularly at one sample per pixel.

Validate the probe during implementation by checking that different explicit
seeds can produce different hashes and that repeated use of one seed produces
the same hash. If the standard uniform-sensor scene does not make enough RNG
work observable, use a benchmark-local randomized sensor through htracer's
public component extension interface. Do not expose or call private generator
providers.


8. Canonical quick suite
------------------------

Define canonical cases as explicit data, not generated from a general matrix.
Use stable IDs prefixed by a workload version, for example:

  quick.v1/mixed/deterministic/f32/seq
  quick.v1/mixed/randomized-seeded/f64/par
  quick.v1/rng-probe/unseeded/spp1/f64/seq

Initial case groups:

1. Mixed deterministic
   * float and double
   * seq and par
   * 4 cases

2. Mixed randomized, fixed seed and moderate samples
   * float and double
   * seq and par
   * 4 cases

3. RNG probe
   * seeded and unseeded
   * seq and par
   * low and moderate samples
   * double
   * 8 cases

Total initial cases: 16.

The calibrated quick.v1 values are:

* Mixed deterministic: 640x360.
* Mixed randomized: 320x180, 8 samples per pixel.
* RNG probe: 640x360, with 1 and 16 sample cases.
* Every case: one warmup and five measured repetitions.

These parameters are part of quick.v1. A material future change requires a new
workload version rather than silently changing the existing case IDs.

--list prints suite name, stable case ID, and a concise effective
configuration. It performs no scene construction or rendering.


9. Measurement harness
----------------------

Implement one typed function that accepts a callable returning
htracer::rendering::image<Float>.

For each warmup:

1. Invoke the callable without timing.
2. Validate and hash the image.
3. Combine the hash into the same run checksum that will be printed and
   serialized.

Warmup results must be consumed too; otherwise an optimizer could remove work
that is intended to initialize code paths, thread pools, or thread-local RNG.

For each measured repetition:

1. Record steady_clock::now().
2. Invoke the render callable and retain its returned image.
3. Record steady_clock::now() immediately after return.
4. Convert the elapsed duration to integer nanoseconds and store it.
5. Validate and hash the image outside the timed interval.
6. Combine the image hash into the run checksum.
7. Destroy the image after validation; destruction is not timed.

Do not batch multiple renders into one timing interval. Fixed workloads should
be calibrated so a single render is long enough to measure. This preserves the
meaning of render-call latency and avoids mixing image destruction or checksum
work into the measurement.

Sort a copy of the raw durations to calculate minimum, median, and maximum.
For an even sample count, define the integer median as the overflow-safe
midpoint of the two central nanosecond values. Retain original raw sample order
in JSON. Treat a zero median as a measurement error rather than dividing by
zero when deriving throughput.

Use the median duration for throughput:

  pixels_per_second = width * height / median_seconds

  primary_samples_per_second =
      width * height * effective_samples_per_pixel / median_seconds

Use an effective sample count of 1 for deterministic rendering. Perform count
products in a sufficiently wide type before converting to floating point.


10. Image validation and hashing
--------------------------------

Validation checks:

* Image width and height match the requested resolution.
* Pixel count equals width * height.
* Every color channel is finite.

Use one documented 64-bit byte-hash algorithm, such as FNV-1a, over:

* Width and height.
* Every floating-point channel's object representation, obtained with
  std::bit_cast or an equivalent defined byte view.

Hash every warmup and measured result outside timed regions. Combine all image
hashes into one reported run checksum. Printing/serializing the checksum makes
both warmup and measured results observable to the optimizer. The checksum may
therefore change if the configured warmup or repetition count changes, which is
acceptable because it is diagnostic rather than an image identity.
Use an ordered hash-combine operation rather than plain XOR so repeated
identical images do not cancel each other.

For deterministic and explicitly seeded cases, require all measured hashes in
that case to match. Do not require unseeded hashes to differ; equality is
possible for small or simple images.

The hash algorithm is stable within the report schema but is not a portable
golden-image contract across architectures, standard libraries, compilers, or
htracer versions.


11. Console and JSON reporting
------------------------------

11.1 Console

Print environment metadata once, followed by one compact row per result:

  ID | median ms | min ms | max ms | Mpixel/s | Mprimary-sample/s | checksum

Parameters not visible in the ID should appear in a short configuration line
or expanded --list output. Do not print every raw sample by default; they remain
available in JSON.

Print each completed case promptly so a long suite shows progress. Keep all
results in memory for final JSON output; the expected result count is small.

11.2 JSON

Write a project-specific serializer with std::ostream. Do not implement a
general JSON DOM or parser. Provide one string-escaping helper, use the classic
locale for numeric output, check stream failures, and return an error if the
output file cannot be completed.

Proposed top-level shape:

  {
    "schema_version": 1,
    "workload_version": 1,
    "environment": {
      "os": "windows|linux",
      "architecture": "x86_64|...",
      "compiler": "msvc|gcc",
      "compiler_version": "...",
      "build_type": "Release",
      "logical_processors": 16
    },
    "results": [ ... ]
  }

Each result contains:

* Stable ID and canonical/custom flag.
* All effective render and measurement configuration fields.
* Raw samples_ns as integers in execution order.
* minimum_ns, median_ns, and maximum_ns.
* pixels_per_second and primary_samples_per_second.
* Seed as a decimal string when present, and checksum as a hexadecimal string,
  to avoid JSON-number precision loss for 64-bit values in downstream
  JavaScript tools.

Serialize absent seed, sample count, or geometry count as JSON null rather than
omitting fields. This keeps the initial schema regular and easy for future
scripts to consume.

11.3 Metadata implementation

Use compile-time platform/compiler macros for OS, architecture, compiler, and
compiler version. Obtain logical processor count from
std::thread::hardware_concurrency(). Inject the configured CMake build type as a
private compile definition for the benchmark target.

Do not add Git commands, CPU model APIs, timestamps, or detailed flag discovery
to the MVP. They can be appended to environment in a later schema-compatible
revision.


12. Error handling and exit codes
---------------------------------

Use a small set of process outcomes:

* 0: requested operation completed successfully.
* 1: runtime failure, validation failure, allocation failure, or output failure.
* 2: invalid CLI usage.

Catch std::bad_alloc and ordinary std::exception at the main boundary and print
concise diagnostics. Internal code should return expected error information or
throw standard exceptions consistently; do not create a large custom error
hierarchy.

If a suite case fails, stop and return failure. Do not write a report that looks
complete unless the JSON explicitly supports partial-run status; partial
reports are deferred from the MVP.


13. CMake integration
---------------------

13.1 Top level

Replace HTRACER_BUILD_RAY with:

  option(
      HTRACER_BUILD_APPS
      "Build the applications. Default: ${PROJECT_IS_TOP_LEVEL}."
      ${PROJECT_IS_TOP_LEVEL})

When HTRACER_BUILD_APPS is enabled, the top level adds the existing apps
directory. apps/CMakeLists.txt unconditionally adds both application
subdirectories:

  add_subdirectory(ray)
  add_subdirectory(benchmarks)

Remove HTRACER_BUILD_RAY rather than retaining a compatibility alias. Rename
the corresponding CMake preset fragment, Nix build argument/flag, and user
documentation to BUILD_APPS.

13.2 Benchmark target

apps/benchmarks/CMakeLists.txt should:

* Add htracer.apps.benchmarks.
* Add implementation files from src as PRIVATE sources.
* Add headers from include/htracer_benchmarks as a PRIVATE FILE_SET HEADERS,
  with apps/benchmarks/include as BASE_DIRS.
* Link privately to htracer::htracer.
* Request cxx_std_23 explicitly.
* Set OUTPUT_NAME to htracer-benchmarks.
* Set EXPORT_NAME to benchmarks-app.
* Inject the build-type metadata definition.
* Install the executable with EXPORT htracer-targets, matching the ray app.
* Register a CTest named benchmarks.list that invokes the target with --list.

Conceptual target definition:

  set(target_name htracer.apps.benchmarks)

  add_executable(${target_name})

  target_sources(
      ${target_name}
      PRIVATE
          src/main.cpp
          src/cli.cpp
          src/render_benchmark.cpp
          src/suite.cpp
          src/report.cpp
      PRIVATE
          FILE_SET HEADERS
          BASE_DIRS
              "${CMAKE_CURRENT_SOURCE_DIR}/include"
          FILES
              "${CMAKE_CURRENT_SOURCE_DIR}/include/htracer_benchmarks/model.hpp"
              "${CMAKE_CURRENT_SOURCE_DIR}/include/htracer_benchmarks/cli.hpp"
              "${CMAKE_CURRENT_SOURCE_DIR}/include/htracer_benchmarks/scenes.hpp"
              "${CMAKE_CURRENT_SOURCE_DIR}/include/htracer_benchmarks/render_benchmark.hpp"
              "${CMAKE_CURRENT_SOURCE_DIR}/include/htracer_benchmarks/suite.hpp"
              "${CMAKE_CURRENT_SOURCE_DIR}/include/htracer_benchmarks/report.hpp"
  )

  target_compile_features(${target_name} PRIVATE cxx_std_23)

  target_link_libraries(
      ${target_name}
      PRIVATE
          htracer::htracer
  )

  set_target_properties(
      ${target_name}
      PROPERTIES
          OUTPUT_NAME htracer-benchmarks
          EXPORT_NAME benchmarks-app
  )

  install(
      TARGETS ${target_name}
      EXPORT htracer-targets
  )

  add_test(
      NAME benchmarks.list
      COMMAND ${target_name} --list
  )

The PRIVATE HEADERS file set adds its BASE_DIRS to the target's build include
directories. Because it is private, the internal headers are not installed or
exported as an application interface. Only the executable runtime artifact is
installed. No target_include_directories() call is needed. Header file sets and
this include-directory behavior are supported by the project's existing CMake
3.25 minimum.

The CTest registration provides a portable smoke invocation without hardcoding
the executable path in GitHub Actions. It performs no timed rendering.

13.3 Presets

Rename the hidden build-ray preset fragment to build-apps and set
HTRACER_BUILD_APPS=ON. Replace build-ray with build-apps in the existing
development and GitHub CI presets. Dedicated benchmark-only presets are not
added: application-enabled configurations intentionally build both ray and
benchmarks.

The Nix buildRay argument and HTRACER_BUILD_RAY CMake flag become buildApps and
HTRACER_BUILD_APPS. Quality derivations that currently enable ray should enable
apps and therefore compile both executables.


14. CI behavior
---------------

The existing Windows and GCC jobs already configure, build, and run CTest.
Their renamed build-apps preset fragment builds both ray and benchmarks, so
benchmarks.list runs as part of the existing Test step.

No workflow timing logic, result artifact, scheduled run, threshold, or
baseline is added. CI validates only that:

* All benchmark templates compile on MSVC and GCC.
* The executable starts.
* CLI registration/listing succeeds.


15. Verification during implementation
--------------------------------------

Permanent automated verification:

* Existing library tests continue to pass.
* benchmarks.list passes on Windows and Linux CI.
* JSON produced by a local small run is syntactically valid during development;
  a permanent general JSON-parser dependency is not added.

Implementation-time checks before declaring the MVP complete:

* Run deterministic and randomized custom cases for float/double and seq/par.
* Run seeded and unseeded RNG-probe cases.
* Confirm deterministic and seeded repetition hashes are stable.
* Confirm at least two selected seeds can affect the RNG-probe hash.
* Confirm traversal output remains unchanged while geometry count increases.
* Confirm invalid CLI combinations fail with exit code 2.
* Confirm JSON contains raw samples and every effective parameter.
* Run the quick suite on Windows/MSVC and Linux/GCC.
* Confirm quick-suite runtime fits the budget after calibration.
* Run git diff --check and the normal project build/test commands.

If convenient without introducing a dependency, validate generated JSON in a
development command using an already available system tool. This is a
verification step, not a project requirement.


16. Extension strategy
----------------------

Future work should extend existing seams:

New scene
  Add a scene_kind value, parser spelling, typed scene factory, validation
  rules, and serialized value.

New component choice
  Add an enum value and one explicit dispatch branch. Promote the corresponding
  field to a CLI option only when a real experiment needs it.

New numeric scene parameter
  Add an optional/effective configuration field and serialize it. A future
  external script varies it by invoking one configuration at a time.

New canonical suite
  Add an explicit function returning benchmark_case values. Do not create a
  generalized matrix language.

New statistic
  Derive it from samples_ns in reporting. Raw samples preserve the required
  input.

New metadata
  Append a field under environment. Increment schema_version only for a
  breaking structural/semantic change, not for an optional additive field if
  consumers are specified to ignore unknown fields.

Future report/sweep tooling
  Consume JSON as a separate program or script. Do not couple graphing or Git
  checkout management into the benchmark runner.

If microbenchmarks later require compiler barriers, automatic calibration, or
nanosecond-scale fixtures, reassess Google Benchmark or another dev-only
library then. The whole-render runner and its result schema can remain useful
even if low-level benchmarks adopt a different harness.


17. Ordered implementation plan
-------------------------------

Step 1: Build skeleton

* Replace BUILD_RAY with BUILD_APPS across CMake, presets, Nix, and docs.
* Add apps/benchmarks with src and include/htracer_benchmarks, the installed and
  exported target, private header file set, and --help/--list skeleton.
* Add model enums/structures and quick-case registration without rendering.
* Add benchmarks.list CTest.

Step 2: CLI and validated configuration

* Implement strict numeric/enum parsing and mode selection.
* Resolve custom options into a complete render_configuration.
* Add clear validation diagnostics and exit codes.

Step 3: Render path and scenes

* Implement typed dispatch and mixed/traversal/rng-probe factories.
* Implement deterministic/randomized and seeded/unseeded calls.
* Keep only render() inside the measured callable.

Step 4: Measurement correctness

* Add warmup consumption, steady-clock samples, validation, hashing, and
  deterministic/seeded hash checks.
* Add median/minimum/maximum and throughput calculation.

Step 5: Reporting

* Add console progress/table output.
* Add metadata and versioned JSON output.
* Exercise JSON and failure paths locally.

Step 6: Quick suite and calibration

* Fill the 16 proposed canonical cases.
* Measure on Windows and Linux.
* Adjust resolution/sample parameters to meet duration and noise goals.
* Freeze quick.v1 IDs and parameters.

Step 7: CI and documentation

* Confirm application-enabled CI presets compile both ray and benchmarks.
* Confirm CTest invokes only --list.
* Document developer build/run commands and comparison conditions.
* Run the complete project verification.


18. MVP definition of done
--------------------------

The implementation is ready when:

* HTRACER_BUILD_APPS builds both ray and benchmarks in Release on Windows/MSVC
  and Linux/GCC.
* Installing an application-enabled build installs/exports both executables but
  does not install the benchmark application's private headers.
* --list, --suite quick, and one fully specified --benchmark render work.
* Custom traversal geometry count, resolution, rendering mode, samples,
  precision, policy, and seed are represented and validated correctly.
* The quick suite intentionally covers float/double, seq/par, and
  seeded/unseeded rendering.
* A timing interval contains only one public render() call.
* Warmup and measured images are consumed, and measured durations remain raw in
  JSON.
* Deterministic and seeded results are checked for within-run reproducibility.
* Console and JSON results contain stable IDs, effective parameters, basic
  environment metadata, summaries, throughput, and checksums.
* The calibrated quick suite stays within the agreed runtime budget.
* CI compiles the executable and runs only benchmarks.list, with no performance
  assertion.
* No external dependency, parameter-sweep engine, comparison tool, graphing
  code, or unrelated library optimization is introduced.


19. Calibration outcome
-----------------------

The accepted quick.v1 parameters are recorded in section 8 and in the canonical
case registry. The RNG probe uses one ambient sphere offset across the camera
view so randomized pixel jitter changes observable silhouette hits. On the
initial Windows/MSVC calibration machine, the complete quick suite takes about
55 seconds. In the clean Linux/GCC 14 container verification it takes about
13 seconds. Both leave substantial room under the agreed few-minute budget.

The JSON report records every effective parameter, so later measurements on
slower development hardware can identify whether a quick.v2 workload is
warranted without making quick.v1 results ambiguous.
