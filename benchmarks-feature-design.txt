HTRACER BENCHMARKS FEATURE DESIGN
=================================

Status
------

This document is a proposed development plan. It does not describe an
implemented feature yet.


1. Purpose
----------

Add standardized, dependency-free benchmarks that answer:

  "On the same machine and build configuration, is the current htracer
   checkout faster or slower than another checkout, and by how much?"

The primary concern is whole-image rendering throughput. Narrower diagnostic
benchmarks are included only where they help explain changes in holistic
rendering performance.

The feature must work on Windows with MSVC and Linux with GCC. It must fit the
project's self-contained design and use only htracer, CMake, and the C++
standard library.


2. Main design decisions
------------------------

* Time the public renderer API rather than private implementation functions.
* Provide a small internal benchmark harness instead of adding Google
  Benchmark or another dependency.
* Treat the benchmark runner as an installed htracer application alongside the
  ray application.
* Provide a quick canonical suite that completes within a few minutes.
* Support one fully specified experiment per CLI invocation. Future external
  scripts can perform parameter sweeps and generate graphs or reports.
* Implement canonical suites using the same parameterized experiment machinery.
* Produce readable console output and versioned JSON containing raw timings,
  parameters, metadata, and summaries.
* Compile and smoke-test the benchmark executable in CI, but do not enforce
  performance thresholds on GitHub-hosted runners.

This design deliberately distinguishes the initial minimum viable product
(MVP) from later development. The MVP should establish interfaces and data
structures that can grow, but it should not implement every anticipated scene,
parameter, suite, statistic, or report.

2.1 MVP scope

The first implementation includes:

* One executable and one timing harness.
* One internal experiment-configuration model shared by suites and custom runs.
* The --suite quick, --benchmark render, and --list entry points.
* Mixed, traversal, and low-complexity RNG probe scenes.
* Rendering mode, geometry count, resolution, sample count, precision, policy,
  and seed as the initial custom experiment parameters.
* Intentional coverage of float/double, seq/par, and seeded/unseeded rendering.
* Warmup, repetitions, raw durations, median, minimum, and maximum.
* Image validation and checksumming outside the timed region.
* Console output and optional JSON output.
* Release builds on Windows/MSVC and Linux/GCC, with CI build and --list checks.

2.2 Future-facing design requirements

The configuration and result models should permit new scenes, lights,
components, metrics, and metadata without redesigning the harness. Later work
may add focused suites, density and reflective scenes, light-count scaling,
thin-lens experiments, richer statistics, comparison/reporting tools, and more
environment metadata. These are roadmap items, not MVP requirements.


3. What is timed
----------------

The principal timed operation is exactly one call to:

  renderer.render(...)

This includes:

* Allocation and zero-initialization of the pixel buffer.
* Sampler and generator-provider setup performed inside render().
* Work-range construction and execution-policy dispatch.
* Primary, shadow, and reflected-ray tracing.
* Construction and return of the image object.

This excludes:

* Scene construction.
* Camera, lens, sensor, batcher, and renderer construction.
* Warmup work.
* Result validation and checksum calculation.
* PPM serialization and filesystem I/O.
* Benchmark result formatting and output.

Including pixel allocation is intentional: it is currently an unavoidable
cost of a public render() call. PPM serialization is not part of the core
library rendering measurement and could only be added later as a separate
I/O benchmark.


4. Relevant implementation characteristics
--------------------------------------------

The current render path has several dimensions worth measuring:

* Unseeded sequential randomized rendering creates and seeds one random engine
  per render.
* Unseeded parallel randomized rendering uses one thread-local engine per
  participating thread and reuses it across pixels and later renders.
* Seeded rendering creates a seed sequence and random engine for every pixel,
  for both sequential and parallel policies.
* Seeded-engine construction should therefore be most visible at low samples
  per pixel and become amortized as the sample count increases.
* Scene intersection scans all objects. Intersection cost is therefore expected
  to grow approximately linearly with object count for a fixed set of rays.
* Every processed light may issue another complete scene intersection for a
  shadow ray. Object count and light count can interact multiplicatively.
* Reflective materials can recursively generate more rays, up to the currently
  hardcoded maximum depth.
* The column and pixel batchers use different task granularity and memory-access
  patterns.
* Float and double affect arithmetic, standard math functions, image-buffer
  size, and cache behavior.
* std::execution::par may use different backends on MSVC and GCC. Results are
  valid for the reported toolchain and environment; timings from different
  platforms must not be directly compared.


5. Proposed source and build structure
--------------------------------------

Proposed directory:

  apps/
    benchmarks/
      CMakeLists.txt
      src/
        main.cpp
        ...
      include/
        htracer_benchmarks/
          ...

The exact file split should remain pragmatic. These names describe logical
responsibilities and do not require unnecessary abstractions.

Proposed target:

  htracer.apps.benchmarks

Proposed executable name:

  htracer-benchmarks

Top-level option:

  HTRACER_BUILD_APPS

HTRACER_BUILD_APPS replaces HTRACER_BUILD_RAY and retains the existing
PROJECT_IS_TOP_LEVEL default behavior. When enabled, apps/CMakeLists.txt adds
both ray and benchmarks. Both executables are installed and exported through
htracer-targets; the benchmark target uses EXPORT_NAME benchmarks-app.

The benchmark application's internal headers live under
apps/benchmarks/include/htracer_benchmarks and are included as, for example,
<htracer_benchmarks/cli.hpp>. They are a PRIVATE HEADERS file set: its BASE_DIRS
provides the build include path, while the headers themselves are not installed
or exported as a public interface.

Existing presets and Nix arguments that refer to BUILD_RAY should be renamed to
BUILD_APPS. Dedicated benchmark-only presets are unnecessary. The tradeoff is
that enabling applications builds both executables, including the benchmark's
template instantiations; this coupling is accepted for the simpler MVP.


6. CLI model
------------

The CLI supports two complementary modes.

6.1 Canonical suites

The MVP provides one canonical suite containing fixed, versioned
configurations for routine checks:

  htracer-benchmarks --suite quick

The executable should also support:

  htracer-benchmarks --list

Canonical cases must have stable identifiers. If their scene or workload is
materially changed, the case identifier or workload schema version must change
so old and new results are not silently treated as equivalent.

Canonical identifiers are presentation values derived from the versioned,
validated benchmark definition. The domain model does not maintain a separate
string or enum identity that could disagree with the definition. A single
quick-suite catalog owns the resolved canonical cases and is the only code that
can give a benchmark canonical provenance.

6.2 One parameterized experiment

One invocation describes one experiment point. The executable does not parse
lists or ranges and does not perform parameter sweeps. For example:

  htracer-benchmarks --benchmark render \
    --scene traversal \
    --geometry-count 64 \
    --width 640 \
    --height 360 \
    --rendering randomized \
    --samples 16 \
    --precision double \
    --policy par \
    --seed 1234 \
    --warmup 1 \
    --repetitions 9 \
    --output result.json

A future script can invoke this command repeatedly while varying one parameter,
then use the JSON results to plot time against object count, samples, pixels,
or another dimension. Such orchestration and graph generation are out of scope
for this feature.

6.3 Proposed benchmark kinds

The MVP exposes only render. It performs a whole-render experiment using a
fixed or generated scene. Selecting the RNG probe scene provides the RNG
diagnostic without requiring a separate CLI kind.

Additional benchmark kinds should only be introduced later when their valid
parameter set or measurement boundary is genuinely different. A separate
"scaling" kind is not needed because a generated render scene already accepts
numeric parameters.

6.4 Proposed parameters

General measurement parameters:

* --warmup N
* --repetitions N
* --output PATH

Initial rendering parameters:

* --scene mixed|traversal|rng-probe
* --geometry-count N
* --width N
* --height N
* --rendering deterministic|randomized
* --samples N
* --precision float|double
* --policy seq|par
* --seed none|INTEGER

The selected scene and rendering mode determine batcher, sensor, lens, lights,
and materials. Choices with only one supported value are executor details, not
single-value configuration fields. Reporting still records their effective
values. Promote a choice into a typed domain alternative only when the
application actually supports more than one value.

The CLI must validate combinations instead of silently ignoring arguments. For
example:

* A deterministic point-sensor/pinhole render does not accept samples or seed.
* A randomized render requires a positive sample count.
* Geometry count is only valid for the traversal scene.
* Width, height, repetition count, and sample count must be positive.
* Custom counts need documented safety limits or explicit overflow checks.

The public API currently hardcodes maximum reflection depth to 5. The benchmark
must not expose a bounce-count argument that it cannot actually control. A
reflective scene can vary whether recursion occurs, but cannot promise an exact
number of bounces. If maximum depth later becomes a public tracer setting, it
can become a benchmark parameter naturally.


7. Scene definitions
--------------------

All scene generators must be deterministic and must run outside the timed
region.

mixed
  The principal representative scene. It should be based on the current ray
  application: several spheres and planes, two lights, and some reflective
  material. Its contents remain fixed for stable comparisons.

traversal
  A controlled scene for measuring intersection traversal scaling. It retains
  one fixed visible object and adds deterministic geometry that is not hit and
  does not change the visible result. --geometry-count means the total number
  of scene objects, not the number added; it must be at least 1. This isolates
  the cost of scanning and rejecting more objects.

density
  Future development. A generated scene in which additional objects are
  visible. This measures
  holistic scene-complexity scaling, including changed hit rates, shading,
  shadows, and potentially reflections. It does not isolate traversal cost.

reflective
  Future development. A fixed scene designed to exercise recursive reflected
  rays. It can be
  inspired by the disco-ring example but must use a workload appropriate for
  benchmarking.

rng-probe
  A deliberately low-complexity scene used with a uniform sensor. Its visible
  result must depend on randomized sample coordinates so RNG work cannot be
  removed as dead code, while its geometry, lighting, and materials keep the
  traced work small and stable. One suitable design places a simple object edge
  across pixels so jitter changes observable hit/miss results. The final design
  must be verified by inspecting hashes or images during implementation.

  A truly empty scene is not suitable: every output pixel would be black
  regardless of the generated coordinates, allowing an optimizing compiler to
  remove some or all RNG-dependent work.

The MVP implements mixed, traversal, and rng-probe. The distinction between
traversal and a future density scene remains important: both can plot time
against geometry count, but they answer different questions and must not share
an ambiguous benchmark name.


8. Canonical workload matrix
----------------------------

The suite must avoid a complete Cartesian product. Each case should answer a
specific question.

8.1 Quick suite

Target runtime: normally under three minutes, with four minutes as the design
ceiling on the supported development machines.

Initial groups:

1. Mixed deterministic render
   * Point sensor and pinhole lens.
   * Column batcher.
   * Float and double.
   * Sequential and parallel policies.

2. Mixed seeded randomized render
   * Uniform sensor and pinhole lens.
   * Fixed moderate sample count and seed.
   * Column batcher.
   * Float and double.
   * Sequential and parallel policies.

3. RNG diagnostic
   * Low-complexity RNG probe scene with observable randomized output.
   * Uniform sensor and pinhole lens.
   * Seeded and unseeded.
   * Sequential and parallel policies.
   * Low and moderate sample counts.
   * Double initially; the extended RNG suite covers both precisions.

The calibrated quick.v1 workloads use 640x360 for mixed deterministic cases,
320x180 with 8 samples per pixel for mixed randomized cases, and 640x360 with
1 or 16 samples per pixel for RNG-probe cases. Every case uses one warmup and
five measured repetitions. These values are fixed parts of quick.v1; a material
future change requires a new workload version.

8.2 Future workload development

After the MVP has been used and its results evaluated, focused suites may be
added for RNG scaling, batching, generated-scene scaling, and scene types. A
longer full suite may eventually be the union of selected canonical cases.

Likely future experiments include seeded/unseeded rendering at several sample
counts, column versus pixel batchers, light-count scaling, visible-object
density, thin lenses, and reflective scenes. They should be added selectively,
not as a complete Cartesian product.


9. Timing and statistical method
--------------------------------

Use std::chrono::steady_clock to measure wall-clock duration. Wall-clock time is
appropriate because parallel throughput is the target.

For each case:

1. Construct the scene, camera, components, and renderer.
2. Perform the configured number of unmeasured warmup renders.
3. Time each measured render independently.
4. Stop the timer as soon as render() returns.
5. Validate and hash that image outside the timed region.
6. Retain every raw duration.
7. Calculate summary statistics after all repetitions.

Recommended defaults:

* Quick suite: 1 warmup and 5 measured repetitions.
* Custom run: 1 warmup and 9 measured repetitions.

Both remain configurable. Cases should be sized so one render lasts at least
tens of milliseconds. Do not subtract clock overhead and do not automatically
discard outliers.

The MVP reports every raw duration plus median, minimum, and maximum render
duration. These are enough to expose obvious spread without implying more
statistical confidence than a small sample provides. Mean, standard deviation,
median absolute deviation, and variability warnings can be considered later
after observing real benchmark behavior. No universal variability threshold
should be assumed in advance.

Warmups intentionally measure steady-state throughput. In particular, they may
initialize the parallel runtime and thread-local random engines. Measuring true
cold process startup would require a different process-level benchmark and is
not part of the initial feature.


10. Preventing invalid optimization and checking results
--------------------------------------------------------

Every measured image must be observably consumed after timing. Compute a stable
64-bit hash over its pixel representations and combine the hashes from all
repetitions into a value printed and written to JSON.

Hashing is not timed. It serves three purposes:

* Prevent the compiler from treating render results as unused.
* Detect accidental empty/no-op rendering.
* Help detect unexpected differences while developing benchmark cases.

Also validate image dimensions and verify that every channel is finite. A
seeded or deterministic case may check that repetition hashes match within one
run. Hashes are diagnostic and must not be treated as portable golden values
across standard libraries, platforms, compiler configurations, or htracer
versions.

The process exits nonzero for invalid arguments or correctness/validation
failures. It does not exit nonzero because a render is slower than an earlier
result.


11. Reported metrics
--------------------

Each result should report:

* Median render time.
* Minimum and maximum render time.
* Pixels per second.
* Primary pixel-samples per second, calculated as:

    width * height * samples_per_pixel / seconds

  Deterministic rendering uses an effective sample count of 1.

Do not label primary samples per second as total rays per second. Shadow and
reflected rays are data-dependent and are not currently counted.

Parallel/sequential speedups, float/double ratios, and other comparisons can be
calculated by future report tooling from the individual results. They do not
belong in the MVP runner.


12. Output design
-----------------

Default output is a compact, human-readable console table. A specified output
path writes versioned JSON.

JSON should include:

Run metadata:

* Output schema version.
* Benchmark workload schema version.
* OS and architecture.
* Compiler name and version.
* CMake build type.
* Logical processor count.

Timestamp, Git revision/dirty state, and detailed compiler flags are useful
future additions, but they should not delay the MVP. Users must initially
record which checkout and build configuration produced a saved result.

Per-result data:

* Stable benchmark identifier.
* Whether the case is canonical or custom.
* Benchmark kind.
* Scene and every supplied/effective parameter.
* Warmup and repetition counts.
* Individual durations, preferably stored as integer nanoseconds.
* Summary statistics.
* Derived throughput values.
* Combined measured-image checksum and, when warmups are present, a separate
  warmup checksum.

JSON is preferred over CSV because it can retain nested metadata and raw sample
arrays without awkward encoding. A future comparison or graphing tool can read
the JSON without changing the benchmark executable.


13. Manual comparison workflow
------------------------------

Example:

  htracer-benchmarks --suite quick --output before.json
  # Modify and rebuild htracer in the same configuration.
  htracer-benchmarks --suite quick --output after.json

Meaningful comparisons require the same:

* Physical machine.
* Power and thermal configuration.
* Compiler and compiler version.
* Build type and relevant compiler flags.
* Benchmark workload version and parameters.
* Approximate background-load conditions.

For careful comparisons, close unnecessary applications, avoid running under a
debugger, use a stable power mode, and repeat suspicious results. Absolute
timings from Windows/MSVC and Linux/GCC should not be compared as if they were
measurements of only the operating-system difference.


14. CI integration
------------------

Initial CI behavior:

* Configure and build the benchmark executable in Release mode on Windows/MSVC
  and Linux/GCC.
* Run htracer-benchmarks --list as a fast executable and registration smoke
  test.
* Do not run the timed suites during normal push or pull-request CI.
* Do not enforce performance thresholds.

GitHub-hosted runner hardware and contention are not stable enough for reliable
regression gating. A future workflow_dispatch job may run the quick suite and
upload its JSON as an informational artifact, but results from different hosted
runners still must not be treated as a controlled time series.

Reliable automated performance gates should wait for persistent, controlled
hardware.


15. Dependency decision
-----------------------

Implement a small internal harness initially.

Google Benchmark would provide mature calibration, filtering, counters, and
reporting, but it adds a development dependency and does not solve unstable CI
hardware. Htracer's primary cases are relatively long whole-render operations,
so the required internal timing code is limited and understandable.

Reconsider a dedicated benchmark library if the project later accumulates many
short microbenchmarks where compiler barriers, automatic iteration calibration,
fixtures, or hardware counters become central requirements.


16. Known limitations and interpretation risks
----------------------------------------------

* std::execution::par does not guarantee ideal scaling or a particular worker
  count. Scheduling, SMT, CPU boost, memory behavior, load imbalance, and the
  standard-library backend all affect results.
* The current Linux toolchain may execute par differently from MSVC, including
  possibly using a serial fallback depending on its standard-library setup.
* An unseeded render follows different random paths on every invocation. The
  RNG probe minimizes tracing variation while keeping RNG-dependent work
  observable; it cannot remove this source of noise completely.
* A density scene changes more than object traversal cost. It must not be used
  to claim an isolated O(N) intersection measurement.
* Light-count and object-count scaling interact because shadow tests scan the
  scene.
* Very small experiments are dominated by timer and dispatch noise.
* Arbitrarily large custom parameters can produce excessive time or memory use;
  inputs require validation and clear documentation.
* Results from different compiler flags, especially architecture-specific
  optimization or link-time optimization, are separate configurations.


17. Implementation stages
-------------------------

17.1 MVP implementation

Stage 1: Build, configuration, and CLI skeleton

* Replace HTRACER_BUILD_RAY with HTRACER_BUILD_APPS across CMake, presets, Nix,
  and documentation.
* Add the installed/exported benchmark executable under apps/benchmarks, using
  src and include/htracer_benchmarks directories and a PRIVATE HEADERS file set.
* Implement argument parsing, validation structure, case registration, --list,
  and useful --help output.
* Define the stable parameter model used by both custom runs and suites.

Stage 2: Harness and reporting

* Implement steady-clock timing, warmups, repetitions, validation, and image
  hashing.
* Implement median, minimum, and maximum summaries.
* Implement console output and versioned JSON with raw samples and metadata.

Stage 3: Initial scenes and public-API benchmarks

* Implement mixed, traversal, and RNG probe scenes.
* Implement deterministic and randomized render configurations.
* Support float/double, seq/par, and seeded/unseeded rendering where valid.
* Add geometry count, resolution, sample count, precision, policy, and seed to
  custom render configuration.
* Build the first quick suite from these configurations.

Stage 4: Calibration

* Run the quick suite on Windows/MSVC and Linux/GCC.
* Tune fixed resolutions and samples so individual measurements are long enough
  to be meaningful and the suite stays within its runtime budget.
* Observe normal run-to-run variability and document how to interpret it.
* Freeze accepted canonical case identifiers and parameters.

Stage 5: Documentation and CI

* Document building, running, comparison conditions, JSON fields, and result
  interpretation.
* Build on Windows and Linux CI and run only the --list smoke test.

17.2 Future development

After the MVP is in use, extend it according to measured needs. Candidate work
includes:

* Density and reflective scene generators.
* Light-count, batcher, thin-lens, and material parameters.
* Focused RNG, batching, scaling, scenes, and full suites.
* Mean, deviation/dispersion measures, and evidence-based variability warnings.
* More complete compiler, Git, CPU, and run-environment metadata.
* Comparison, sweep, graphing, or report tools outside the benchmark runner.
* A dedicated benchmark library if numerous short microbenchmarks make the
  internal harness inadequate.

The initial experiment configuration and JSON schema should allow these fields
to be added compatibly, but the MVP should not implement unused general-purpose
frameworks for them.


18. Acceptance criteria
-----------------------

The initial feature is complete when:

* A clean Release benchmark build succeeds with Windows/MSVC and Linux/GCC.
* HTRACER_BUILD_APPS builds, installs, and exports both ray and benchmarks; the
  benchmark's private headers are not installed.
* The quick suite completes within the agreed runtime budget after calibration.
* Canonical cases have stable identifiers and complete parameter records.
* A user can run one custom experiment with a chosen rendering mode, geometry
  count, resolution, sample count, precision, policy, and seed mode.
* No list/range parsing or sweep orchestration is present in the executable.
* Float and double, seq and par, and seeded and unseeded randomized rendering
  receive intentional coverage.
* Every measured image is consumed and validated outside the timed region.
* Raw durations, median/minimum/maximum summaries, basic environment metadata,
  throughput, effective parameters, and checksums are available in JSON.
* The implementation has no external runtime or build dependency beyond the
  existing project requirements.
* CI verifies build portability without making timing assertions.


19. Explicitly out of scope
---------------------------

* Optimizing htracer based on benchmark results.
* Graph generation or HTML reports.
* A script that performs parameter sweeps.
* Automatic comparison between Git revisions.
* Committing historical benchmark baselines.
* Performance regression thresholds in ordinary GitHub Actions CI.
* CPU affinity, process-priority, or power-management control.
* Hardware performance counters.
* PPM/file-I/O benchmarking.
* Exposing private generator providers solely for microbenchmarking.
* A configurable bounce-count benchmark until the public tracing API supports
  controlling maximum depth.
